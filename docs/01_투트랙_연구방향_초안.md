# 투트랙 연구 방향 설계 — Phase 1 검토 초안

**상태:** 투트랙, L2 난이도, 공통 도메인 1:1 상담 예약 서비스, 실행 순서 Track 2 → Track 1은 확인됨. 연구 질문·가설·실험 프로토콜은 아직 초안이며 미확정.

## 이번 단계의 범위

먼저 두 연구의 핵심 질문과 경계를 잡는다. 표본 수, 모델 세부 버전, 프롬프트, 통계 분석, 실제 구현 절차는 승인 후 다음 단계에서 정한다.

## 공통 상위 관심

**Coding Agent가 설계 과정에서 더 좋은 소프트웨어 결과를 내도록 하는 방법은 무엇인가?**

두 트랙은 이 상위 관심을 공유하지만 조작하는 대상은 서로 다르다. 연구 질문과 조건 비교는 별개로 두되, 실행은 Track 2 결과에서 Track 1 시작점을 고르는 순서형으로 한다. Track 1의 모든 조건은 같은 동결된 Track 2 결과물에서 출발하므로, Track 1 효과는 그 seed에 조건부로 해석한다. 하나의 2×2 실험으로 합치지 않는다. 공통 도메인은 1:1 상담 예약 서비스이며 구체 요구는 별도 카드 초안에서 검토 중이다.

---

## Track 2 — Revision-aware Design

### 문제

Agent가 초기 설계를 하나의 완결된 정답처럼 취급하면, 나중에 추가되는 요구사항이 초기 결정과 충돌할 때 수정·회귀·재작업이 커질 수 있다. 반대로 모든 것을 처음부터 확장 가능하게 만들면 과잉설계가 생길 수 있다.

### 연구 초점

설계 시점에 요구와 결정을 다음처럼 구분하고, 변경 가능 지점과 재검토 조건을 기록하게 한다.

- 확정된 요구사항과 안정적인 결정
- 잠정 결정과 가정
- 변경이 발생할 수 있는 경계·영향 범위
- 어떤 조건에서 다시 검토할지

### 연구 질문 초안

> 초기 설계에서 확정 요구, 잠정 결정, 가정, 변경 지점 및 재검토 조건을 명시하면, 일반 설계나 막연한 “확장성을 고려하라”는 지시보다 나중에 공개되는 요구사항 변경에 더 잘 대응하면서 과잉설계를 억제할 수 있는가?

### 연구의 중심 결과

**설계 표현 방식이 이후 변경 대응에 주는 효과.** 변경 전 품질도 함께 확인하되, 변경량이 적다는 이유만으로 좋은 설계라고 판단하지 않는다. 최종 주장을 변경 후 기능·회귀·비용 결과에 맞춰 제한한다.

### 범위 경계

앞서 논의한 “계획 품질만 평가하는 파일럿”과 자동으로 같은 범위로 보지 않는다. 변경 대응을 실제로 주장하려면 후속 변경 과제와 코드 수정 또는 검증 가능한 대체 평가가 필요하다.

## Track 1 — Developer-Reasoning Personalization with Compensation

### 문제

개발자마다 설계를 검토하는 반복 패턴이 다르다. 예를 들어 예외 경로를 집요하게 확인하는 습관은 누락을 줄일 수 있지만, 발견한 모든 가능성을 설계에 추가하면 복잡성이 커질 수 있다. Agent가 습관을 단순 모방하는 것과 장점을 활용하면서 부작용을 보정하는 것은 다른 접근이다.

### 연구 초점

성격이나 일반적인 사용자 취향이 아니라, 여러 개발 과정에서 관찰되는 **설계·검토 행동**을 프로필로 만든다. 예시 행동은 예외·실패 경로 탐색, 흐름·상태 검증, 범위 통제, 단순성 검토 등이다. 프로필 항목은 관찰 근거·빈도·맥락·신뢰도를 갖고, 추측을 사실처럼 저장하지 않는다.

### 연구 질문 초안

> 개발자의 반복적으로 관찰된 설계·검토 행동을 Agent의 사전 설계 과정에 적용하면, 같은 일반 검토 절차만 제공하는 것보다 설계와 downstream 구현 품질이 개선되는가? 해당 습관의 체계적 부작용을 명시적으로 보정하면 순수 모방보다 과잉설계를 줄일 수 있는가?

### 연구의 중심 결과

**개발자별 사고·검토 행동을 Agent가 어떻게 활용하고 보정하는가.** 개인화가 단순한 공통 체크리스트보다 나은지, 그리고 이득과 부작용이 함께 바뀌는지 확인한다.

### 범위 경계

한 사람의 프로필만 시험하면 일반 효과가 아니라 단일 사용자 사례 또는 타당성 파일럿이다. 여러 개발자에 관한 일반 주장을 하려면 반복 관찰 자료와 여러 참여자가 필요하다. 프로필을 추출하는 방법과 프로필을 활용하는 방법은 다른 연구 질문이므로, 첫 실험에서 동시에 변화시키지 않는다.

## 두 트랙의 차이

| 구분 | Track 1: 개인화된 설계 사고 | Track 2: Revision-aware |
|---|---|---|
| 핵심 조작 대상 | 개발자의 반복된 검토 행동을 Agent의 설계 절차에 어떻게 적용하는가 | 설계 산출물에 불확실성과 변경 경계를 어떻게 기록하는가 |
| 무엇을 설명하려는가 | 사용자별 사고 패턴이 설계 검토와 구현 결과를 바꾸는 방식 | 설계가 나중의 요구 변경을 견디는 방식 |
| 주요 위험 | 프로필 추론 오류, 일반 체크리스트 효과와의 혼동, 개인별 과적합 | 막연한 확장성으로 인한 과잉설계, 변경 비용 대리측정 |
| 예상 평가 초점 | 경계/실패 조건 누락·구현 품질·복잡성·프로필 정확도 | 숨겨진 변경 요구 후의 성공·회귀·재작업·복잡성 |

두 주제는 별도 연구 질문으로 유지하고, 실행은 Track 2 → Track 1로 이어간다. Track 2 평가에서 사전 기준으로 고른 설계·코드·Stitch 묶음을 고정한 뒤, 그 똑같은 묶음을 Track 1 모든 조건에 제공한다. 따라서 Track 1은 빈 brief에서 프로필 효과를 보는 설계가 아니라, 좋은 Revision-aware 결과물에 개발자 프로필을 추가 적용했을 때의 효과를 본다.

## 현재 근거가 주는 설계 힌트

- 늦게 드러나는 요구사항과 기존 코드 수정 부담은 실제 Agent 연구의 대상이지만, 관찰된 연관만으로 특정 설계 표기의 인과 효과가 증명되는 것은 아니다. Track 2는 그 표기를 조작하는 통제 비교가 필요하다. [Requirements After the First Edit](https://arxiv.org/abs/2609.03028)
- 사용자 모델링과 개발자 개인화는 이미 연구되고 있다. 따라서 Track 1은 “개인화 Agent” 일반이 아니라, **설계 검토 행동의 개인화와 체계적 약점 보정**으로 좁혀야 한다. [TOM-SWE](https://proceedings.mlr.press/v306/zhou26f.html), [Do Personalized Skills Help Coding Agents?](https://arxiv.org/abs/2608.10319)
- 이런 연구들은 방향 설정을 돕는 인접 근거다. 체계적 검색과 자세한 문헌 검토 전에는 어느 트랙도 신규성을 확정하지 않는다.

## 아직 고정하지 않은 결정

1. 각 트랙의 대상 과제는 새 시스템 설계인지, 기존 저장소 변경인지.
2. Track 2의 변경 대응에서 누적 순차 변경을 몇 단계 수행하고, 좋은 결과물을 어떤 사전 기준으로 선정할지.
3. Track 1에서 프로필을 반복 세션으로 자동 추출할지, 사용자 확인을 받은 프로필로 우선 효과를 시험할지.
4. Track 1에서 동결된 Track 2 seed를 검토·개선할 때 사용할 공통 task instruction과 acceptance 기준.
5. 단일 모델 버전과 평가 rubric을 어떤 기준으로 고정할지.

## 이번 단계에서 확인받을 내용

- Track 2 결과를 Track 1의 공통 seed로 삼아, Track 1 결과를 그 seed에 조건부로 해석하는 순서가 연구 의도에 맞는가?
- 각 트랙의 연구 질문 문장이 사용자가 의도한 핵심을 제대로 담았는가?
- 특히 Track 1에서 핵심이 “내 성향을 그대로 따라 하기”가 아니라 **반복 관찰된 유익한 사고 패턴은 활용하고 부작용은 보정하기**라는 표현이 맞는가?

> 확인이 끝나면 승인된 연구 방향을 결정 요약에 고정하고, 다음 단계에서 각 트랙의 구성개념·가설·실험 변수와 평가 방법을 따로 설계한다.
