# FlowSpec-Gemma4: 트랜잭션 코드 생성에서 실행 순서와 메서드별 규칙 적용 범위

**부제:** 보존된 46회 실행과 30개 관측의 후속 비교로 살펴본 로컬 Gemma 4 코딩 에이전트의 순서 효과와 한계

## 1. 초록

본 연구는 설계 명세의 표현 방식이 로컬 코딩 에이전트의 SQLite 예약 엔진 구현에 미치는 영향을 분석한다. 보고된 모델은 `llama.cpp`에서 구동한 **Gemma 4 31B-IT**이며, 컨텍스트 창은 `12,288` 토큰, `temperature=0.2`다. 분석 대상은 **고유 실행 46회**로, 두 규모 과업에 대한 기존 22회와 V2 추가 실행 24회로 구성된다. 후속 비교는 기존 실행 6개를 재사용하여 **조건별 n=10, 총 30개 관측**으로 구성했다. 번호가 있는 실행 흐름, 번호를 제거하고 섞은 흐름, 메서드별 멱등성 규칙의 적용 범위를 추가한 실행 흐름을 비교한다.

보존된 30개 구현에 외부 요구사항 검증 8개를 다시 실행한 결과, 전체 통과는 각각 **5/10, 4/10, 10/10**으로 재현됐다. 멱등성 조회에 예약 상태 필터가 들어간 구현은 각각 **5/10, 6/10, 0/10**이었다. 범위 표시 조건은 관측된 코드 정확도가 가장 높았지만 토큰 비용도 높았다. 에이전트가 정상 완료한 세션은 **5/10**으로, 나머지 5회는 15스텝 예산을 소진했음에도 남겨진 코드가 외부 검증을 통과했다. 이 결과는 규칙의 적용 경계를 명시하는 기법의 후속 연구를 뒷받침한다. 결정론적 신뢰성, 일반적인 순서 우위, 모델 내부의 attention 메커니즘을 증명하지는 않는다.

## 2. 연구 질문

SOP 기반 에이전트 협업을 다룬 [MetaGPT](https://arxiv.org/abs/2308.00352)처럼 구조화된 개발 절차는 설계와 구현의 분리를 동기로 삼을 수 있다. 본 연구는 작은 로컬 하네스 안에서 전달되는 설계 산출물에 초점을 맞춘다. 서로 관련된 두 과업의 코드 생성 실험이므로, 실제 저장소 이슈 해결을 평가하는 [SWE-bench](https://arxiv.org/abs/2310.06770)의 점수와 직접 비교할 수 없다.

질문은 다음과 같다. (1) 설계 표현에 따라 정확도와 비용이 어떻게 달라지는가? (2) 규칙 내용을 유지하면서 번호를 제거하고 불릿을 섞으면 결과가 달라지는가? (3) 규칙이 적용되는 메서드를 명시하면 취소된 예약의 멱등 재실행 오류가 줄어드는가?

## 3. 방법론

### 3.1 하네스, 과업, 평가 지표

기존 2단계 구성은 단일 턴 Designer가 JSON 설계를 생성하고, 새로운 Coder 작업 공간에 과업과 설계를 전달한다. 도구는 `list_files`, `read_file`, `write_file`, `replace_text`, `run_tests`의 5개다. 고정 설계 후속 실험은 새로운 Designer 호출 없이 저장된 JSON을 주입한다. 프롬프트, 지표, 생성 코드, JSONL 트레이스를 보존했다.

보고된 설정은 Gemma 4 31B-IT `Q4_K_M`, `llama.cpp` 단일 슬롯, `temperature=0.2`, 컨텍스트 `12,288`, 15스텝 예산이다. **예외:** V1 무설계는 40스텝 상한에서 9스텝에 끝났고, 턴당 출력 상한은 V1 Cond 1~3·5가 `3,584`, V1 Flow와 V2가 `4,608`이었다. V2 Flow r1은 타임아웃 300초, 이후 후속 설정은 900초로 기록됐다. 시드는 지정되지 않았다. 메타데이터의 모델 식별자는 `local-model`이며 모델 파일의 불변 해시는 없다.

V1은 2개 테이블·5개 연산·6개 검증의 예약 백엔드다. V2는 **7개 테이블·13개 연산**으로 상담사, 슬롯, 선불 상담권, 멱등 원장, 예약, FIFO 대기열, 감사 로그를 다룬다. 검증은 슬롯 수명주기(REQ-1), 상담권 발급(REQ-2), 예약 생성(REQ-3), 원자적 일정 변경(REQ-4), 승격 없는 취소(REQ-5), 대기열 승격(REQ-6), 정합성 대사(REQ-7), 취소된 예약 재호출(REQ-8)이다. REQ-8은 동일 멱등키 재호출 시 상담권을 다시 차감하지 않고 기존 취소 예약을 반환해야 한다.

**외부 코드 검증**, 에이전트가 작성한 pytest 결과, **하네스 정상 완료**를 구분한다. 예산 소진 세션도 통과 코드를 남길 수 있다. 8개 검증은 모든 입력과 동시성 실행의 정확성을 보장하지 않는다. 평균과 표본 표준편차를 보고한다. 총 토큰은 Designer와 Coder의 호출별 입력·출력 합계이며 반복 전달된 컨텍스트를 포함한다. 혼합된 후속 표본에는 Coder 토큰도 별도로 제시한다.

### 3.2 조건과 표본 구성

기존 22회에는 직접 무설계, 최소 래퍼, 자유 서술, 정적 계약, 선언적 불변식, 번호가 있는 실행 흐름, 비순서 흐름, 행동 체크리스트를 추가한 흐름이 포함된다. 표 1~3은 당시 관측을 유지한다.

- **Flow Base:** 기존 r1~r3과 신규 7회. 초기 3회는 각각 생성된 설계가 서로 다르며, 신규 r4~r10은 r1 설계를 고정한다.
- **Unordered:** r1 Flow의 규칙 내용과 스키마를 유지하면서 번호를 제거하고 불릿을 섞는다. 기존 3회와 신규 7회다. 토큰열이 완전히 같다는 뜻은 아니며 번호와 위치를 동시에 바꾼다.
- **Flow + Scoped:** 고정 Flow 설계의 `create_booking` 1단계와 `scope_rule` 필드에 한국어·영어 설명을 반복한다. 상태와 무관하게 기존 예약을 반환하고, `CONFIRMED` 검사는 변경·취소 자격 판단에만 적용한다고 명시한다. 기존 파일럿 r1과 이후 신규 9회다.

따라서 **22 + 24 = 고유 실행 46회**이며 52회가 아니다. 후속 30개 관측 중 6개는 기존 연구와 겹친다. Scoped는 범위뿐 아니라 의미 내용, 길이, 반복, 언어도 변경한다. 이는 탐색적인 순차 표본이며 무작위 배정·토큰 일치 완전 요인 실험이 아니다. `Unordered + Scoped`는 아직 실행하지 않았다.

## 5. 코드와 트레이스 근거

### 5.1 멱등 재호출의 조건 혼입

반복된 실패 구현은 다음 조회를 사용한다.

```sql
SELECT * FROM bookings WHERE idempotency_key=? AND status='CONFIRMED'
```

취소된 예약은 이 조건에 맞지 않는다. 따라서 재호출은 기존 예약을 반환하지 못하고 새 예약 생성 로직으로 진행한다. 통과 구현은 상태 제한 없이 멱등키로 조회한다. Scoped 명세는 이 경계를 직접 명시한다. 이 패턴은 재호출 조회와 상태 변경 자격 조건을 혼동했다는 해석과 일치하지만 attention을 직접 측정한 결과는 아니며, 인접 메서드 간 간섭이 유일한 원인이라고 확정할 수 없다.

### 5.2 초기 연구의 다른 실패 사례

- **자유 서술(V2):** 승격할 대기자가 없을 때 슬롯을 다시 열어야 하는 분기를 누락해 REQ-5·REQ-7에 실패했다.
- **불변식(r2/r3):** 상담권 발급에 `INSERT OR REPLACE`와 가산 `UPDATE`를 연달아 생성해 최초 잔액을 중복 증가시켰다. 코드에는 기존 문장 교체 대신 수정 내용을 덧붙인 흔적이 있다. 이를 불변식 명세 전체의 일반적 한계로 확대하지 않는다.
- **행동 규칙 추가 흐름(V2):** 잘린 파일 쓰기 인자와 대화 압축이 반복됐고 에이전트 테스트 작성 전에 스텝 예산에 도달했다. 남은 엔진은 외부 검증 7/8을 통과했다.

이 사례는 메서드별 가드, 분기별 사후 조건, 에이전트 테스트와 별개인 최종 코드 검증의 필요성을 뒷받침한다. 모델 인지 과정을 직접 측정한 결과는 아니다.

## 6. 해석, 한계, 다음 실험

초기 연구는 실행 순서가 신뢰성을 높일 가능성을 보였다. 확장 결과에 따라 주장을 좁힌다. **순서만 있는 조건은 전체 통과 5/10, 비순서는 4/10**이었고, 범위 설명을 추가하면 코드 전체 통과 10/10이었지만 비용 증가와 세션 완료율 저하가 동반됐다. 따라서 ‘순서가 규칙보다 중요하다’보다 순서와 적용 범위를 함께 다룬다.

후속 검증할 실무 템플릿은 (1) 무조건적인 기존 기록 재호출 조회, (2) 메서드별 자격·잔액 검사, (3) 원자적 변경, (4) 명시적인 분기와 대체 처리, (5) 로그·반환이다. 기존 기록의 조회와 새로운 상태 변경의 자격 판단을 직접 구분한다. 이 과업에서 근거를 얻은 가설이며 보편적 처방은 아니다.

한계는 서로 관련된 단일 모듈 과업 2개, 보고된 양자화 모델 1개, 미지정 시드, 순차 표본, 초기 Flow의 서로 다른 생성 설계, 타임아웃 차이, 기존 성공 파일럿 포함, 실패를 관찰한 뒤 개발한 개입이다. Scoped 설명은 취소 재호출 의미를 두 언어로 두 번 추가하므로 범위 표시만의 효과를 의미 강조·반복에서 분리할 수 없다. 활성값 분석, 폭넓은 과업 분포, 다른 모델의 독립 재현은 수행하지 않았다.

다음 실험에서는 `Unordered + Scoped`를 추가해 **순서 × 범위**를 완성하고, 하나의 기본 설계를 고정하며, 범위 표시 조건 간 의미 내용과 언어를 맞추고, 표본 포함 기준과 지표를 사전에 정하고, 실행 순서를 균형 있게 배치한다. 이후 범위 문구·반복·언어를 각각 절제한다. 고온 샘플링과 다중 파일 과업도 후속 연구다.

## 7. 재현 방법

[GitHub 저장소](https://github.com/Eunryong/FlowSpec-Gemma4)에 기존 연구 22회와 추가 24회를 보존했다. 후속 표본 명세에는 30개 관측과 중복을 기록했다. CPU만 사용하는 감사 스크립트는 REQ-1~REQ-8을 재실행하고 기존 결과·토큰 합계를 대조하며 조회 SQL과 설계·코드 해시를 기록한다.

```bash
python3 scripts/audit_scope_followup.py
```

회차별 근거는 `research/inputs/scope_followup_cohort.json`, 기존 n=10 요약 JSON 2개, `research/outputs/scope_followup_audit.json`, `docs/scope_followup_results.md`에 있다. 보존된 구현의 재검증과 모델이 동일 코드를 다시 생성하는 것은 구분한다. 이번 제출본 수정 과정에서는 새로운 모델 생성 실험을 실행하지 않았다.
