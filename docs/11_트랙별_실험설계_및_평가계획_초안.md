# 트랙별 실험 설계와 평가 계획 초안

**상태: 두 트랙의 방향만 합의됐고 연구 질문·조건·가설·통계 계획은 미확정입니다.** 아래 condition matrix는 `05`와 `06`을 정리한 제안이며, `research/conditions/`의 placeholder와 동일한 확정 입력이 아닙니다.

## 공통 비교 원칙

- Track 2를 먼저 수행하고, 사전 기준으로 선정·동결한 결과물을 Track 1의 공통 seed로 사용합니다. 연구 질문과 분석은 분리하며 factorial/2×2로 합치지 않습니다. Track 1의 결론은 이 T2 seed에 조건부입니다.
- 조건 외에는 승인 brief, design schema, baseline agent prompt, 도구 집합, model/server build, context, temperature, output budget, 테스트, evaluator rubric을 고정합니다.
- 한 run에는 한 track의 한 condition만 전달합니다. Designer와 Coder 모두 fresh session으로 시작합니다.
- Designer의 최종 JSON만 Coder에게 전달합니다. 중간 대화와 hidden evaluator 정보는 공유하지 않습니다.
- 모든 condition은 같은 **구현 handoff 기준**을 목표로 합니다. 흐름 단계별 입력·출력·검증·상태 변화, 필드 수준 데이터 사전, API·acceptance traceability, flow에 연결된 Stitch 화면·상태 산출물을 같은 패키지로 Coder에게 넘깁니다. 조건별로 바뀌는 것은 설계 전략이지 산출물 요구의 깊이가 아닙니다.
- Track 1의 모든 condition에는 hash가 고정된 동일한 T2 code/design/Stitch/test seed bundle과 동일한 refinement task를 제공합니다. 각 run은 이 seed의 새 복사본에서 시작하고 prior session history는 전달하지 않습니다.
- Stitch 접근·버전·도구 권한·내보내기 경로와 사람의 보정 규칙을 조건 간 고정합니다. 자동 호출 시간과 비용은 tool cost로 남기고, 수동 보정이 있으면 조건을 가린 절차와 작업 시간을 기록합니다.
- 반복 단위, 조건 순서, seed schedule, 참여자별 배치·분석 방식은 실행 전에 정합니다. 현재 harness의 `--repetitions`는 단일 condition 반복을 지원하지만 condition 순서를 자동 randomize하지 않습니다.

## Track 1 — Developer Reasoning Profile + Compensation

### 질문 초안

사전 기준으로 선정한 좋은 Revision-aware seed에 반복 관찰되고 개발자가 확인한 설계·검토 행동을 추가 적용하면 generic 절차보다 개선되는가? 명시적 부작용 보정이 단순 모방보다 과잉 설계를 줄이는가? 결과는 이 seed에 조건부로 해석합니다.

### 조건 후보 (`05` 기준)

| ID | 비교 조건 | 프로필 | 목적 |
|---|---|---:|---|
| T1-A | 일반 설계 기준선 | 없음 | profile 없이 공통 brief만 처리할 때의 기준 |
| T1-B | 모든 참여자에게 같은 고정 검토 checklist | 없음 | 일반 checklist 효과를 분리 |
| T1-C | 관찰 profile을 직접 적용 | 있음 | naive personalization 비교 |
| T1-D | 근거가 있는 장점을 활용하고 부작용/범위를 분류 | 있음 | compensated personalization 비교 |

`T1-C`와 `T1-D`에는 동일한 승인 profile과 동일 brief를 사용합니다. `T1-B`가 빠지면 profile 효과와 일반 edge-case checklist 효과를 분리하기 어려울 수 있습니다. 조건 세트, 표현, 길이와 분석 contrast는 확정 전입니다.

### Profile 준비와 참여자 설계

현재 사용자는 본인을 단일 참여자로 삼고, 제공한 Aside 자료와 접근 가능한 Codex·ChatGPT 작업 기록을 합쳐 profile 초안을 만들도록 요청했다. 근거와 적용 지침 초안은 [13 통합 설계 행동 프로필 자기검토 초안](13_통합_설계행동프로필_자기검토초안.md)에 둔다.

- 현재 프로필은 본인 검토 전이며 실험 입력이 아니다. 이번 요청은 초안을 요약하는 허가로 기록하고, 정식 연구 사용 동의·보관 기간·삭제 절차는 별도로 정한다.
- profile에는 사용자 메시지에서 확인한 반복 행동, evidence ID, 관찰 맥락, 빈도 표현, confidence, expected benefit, side-effect hypothesis를 기록한다. 성격이나 심리 특성은 추정하지 않는다.
- 본인이 근거·맥락·반복 여부·신뢰도·이점·부작용을 검토하고 승인한 후에만 version과 hash를 고정한다.
- 이번 파일럿에서는 profile 추출 규칙은 고정하고, 같은 승인 profile을 T1-C와 T1-D에 적용한다. T1-C와 T1-D 사이에서 달라지는 것은 적용 보정 정책이다.
- T1-A부터 T1-D까지 모든 조건은 같은 구현 handoff schema와 Stitch 기능에 접근합니다. profile 조건만 flow/data/UI 검토 관점이나 선택에 영향을 줄 수 있으며, profile 내용이 승인 brief의 제품 요구로 추가되지는 않습니다.
- Track 1 입력에는 선정된 T2 seed bundle과 고정 refinement task를 포함합니다. 이를 통해 T1-A/B 대 T1-C/D의 차이를 같은 시작점에서 비교합니다.
- 참여자는 1명이므로 결과는 이 참여자와 정한 과제·모델·환경의 탐색적 단일 사례로 제한한다. 개발자 일반으로 일반화하지 않는다.
- 프로필에 없는 특성은 추론해 채우지 않고, profile을 제품 요구처럼 주입하지 않는다.

### 결과 후보

- 승인된 issue/edge-case에 대한 precision과 recall, 근거 적합도
- 기능·경계 조건 테스트 결과와 구현 통과율
- 추가 요구를 수용한 정도와 불필요한 scope/복잡성
- profile evidence와 실제 사용 판단의 일치도 및 confidence calibration
- input/output tokens, latency, tool calls/time

## Track 2 — Revision-aware Design

### 질문 초안

초기 설계에 결정의 안정도, 근거, 영향 관계, 재검토 조건을 기록하면 일반 설계나 막연한 extensibility 지시보다 순차 요구 변경에 잘 대응하면서 과잉설계를 억제하는가? 이 결과들 가운데 Track 1 공통 seed를 사전 선정 규칙으로 하나 동결한다.

### 조건 후보 (`06` 기준)

| ID | 비교 조건 | 초기 설계 representation |
|---|---|---|
| T2-A | 일반 설계 | 승인 initial brief만 사용 |
| T2-B | 일반 extensibility | 변화 가능성을 고려하되 불필요한 복잡성을 피하라는 고정 지시 |
| T2-C | change-aware, 간결성 강조 | 가능성 높은 변화 경계를 식별하되 미공개 요구는 구현하지 않음 |
| T2-D | 명시 decision ledger | `STABLE / PROVISIONAL / ASSUMPTION / OPEN`, 근거, 영향 card, revisit condition 기록 |

초기 단계에서는 어느 조건에도 후속 변경 텍스트·candidate ID·gold tests를 노출하지 않습니다. 조건의 문구와 output schema 관계는 아직 정하지 않았습니다.

### Track 1 seed 선정 규칙 — 본 run 전에 고정

한 개의 “최고 점수 run”을 결과를 본 뒤 임의로 고르지 않습니다. 우선 구현 handoff 산출물 완성, 필수 acceptance 통과, 최종 revision regression 통과를 eligibility gate로 둡니다. 적격 결과 사이에서는 사전 지정한 primary blind quality criterion으로 seed를 고르고, 비용은 별도 보고합니다. primary criterion, 반복 간 집계 방식, 동점/비적격 처리, 실제 seed artifact 선택 절차는 protocol에 미리 기록해야 합니다. 여러 결과가 quality dimension별로 trade-off를 보이면 임의의 종합 점수를 만들지 말고, 사전 등록한 기준으로 seed 선택 여부를 결정합니다.

모든 T2 조건은 동일한 initial brief로 구현 handoff 기준을 충족하는 V1 설계와 Stitch 화면 패키지를 만듭니다. 바뀌는 treatment는 초기 설계에서 변화 가능성을 다루는 방법입니다. 변경이 공개된 뒤에는 영향받은 flow, data/API contract, Stitch 화면·상태, acceptance/regression mapping을 갱신하고, 최초 산출물과 수정본을 모두 보존합니다. Stitch 입력에 후속 change 내용이나 gold test가 노출되어서는 안 됩니다.

### 변경 적용 단위 — 반드시 결정할 항목

두 가지 측정 방식은 결과 해석이 다릅니다.

1. **누적 순차 변경:** CHG-01 적용본에서 CHG-02를 적용하고, 이전 revision 결과가 다음 단계의 시작점이 됩니다. 현재 `run-experiment revise`가 이 방식을 사용합니다. 현실적인 연속 유지보수를 흉내 내지만, 뒤 change 결과에 앞 change의 영향이 포함됩니다.
2. **V1 분기형 독립 변경:** 각 change를 동일 V1 구현에서 별도로 시작합니다. change별 원인 분석은 쉽지만 장기 누적 적응을 측정하지 않습니다. 현재 harness는 change별 V1 branch를 만들지 않습니다.

실험 질문이 cumulative maintenance인지 change-specific effect인지 선택한 뒤, `07` candidate의 개수·내용·순서와 `research/hidden/changes/change_XX.md` 매핑을 동결합니다. 현재 `07`의 JSON 후보는 runner가 직접 읽지 않습니다.

### 결과 후보

- 초기 V1 acceptance, edge-case 결과와 복잡성
- 각 change acceptance와 이전 test suite 회귀 결과
- design ledger가 변경 영향·재검토 조건을 올바르게 지적했는지
- 수정 범위·실패 원인·불필요한 사전 복잡성
- revision별 및 cumulative token/latency/tool 비용

변경 파일 수와 LOC는 참고용 보조 지표로만 둡니다. 변경량이 적다는 사실만으로 좋은 결과라고 보지 않습니다.

## 평가와 분석 원칙

| 축 | 분리 보관할 값 | 초안에 남은 결정 |
|---|---|---|
| 기능 품질 | functional acceptance, 상태·규칙 테스트 | test별 pass 기준과 부분 점수 |
| 경계/실패 | edge-case coverage와 실패 응답 | 포함할 case 및 가중 방식 |
| 회귀/변경 | regression, future-change tests | Track 2 누적/분기 단위 |
| 설계 품질 | 명시 rubric, 카드 trace, 과잉설계 | blind evaluator rubric과 adjudication |
| 비용 | prompt/output/total tokens, TTFT, prefill, generation, total latency, tool calls/time | 누락된 llama.cpp timing 처리와 통계 요약 |
| 실행 품질 | setup 실패, schema 오류, max-step 초과, Stitch 생성/내보내기 실패 | 실패 run 제외/포함 규칙 |

품질과 비용은 따로 보고합니다. 단일 복합 점수나 임의의 “효율 점수”는 만들지 않습니다. 필요하면 Pareto 비교를 추가하되, 사전 정의된 raw metric을 함께 표시합니다.

## 분석 계획 전에 결정할 것

- 모집 가능한 참여자/profile 수와 연구가 주장할 범위
- 실험 단위와 조건 간 배정 방식: within-participant, between-participant 또는 pilot
- 각 조건·참여자별 반복 수와 seed/block pairing
- 테스트별 점수 정의, evaluator 일치도와 disagreement 처리
- 실패 run·불완전 token usage·서버 불안정의 처리
- 사전 분석 계획, 통계 방법, 결과 보고 한계

표본 수나 통계 방법을 아직 임의로 고정하지 않습니다. 이 항목은 연구 질문과 참여자 구조가 확정된 다음 별도 protocol version에 기록합니다.

## 현재 harness와의 간극

- 현재 condition `.md` 템플릿은 각 트랙 3개 이름으로만 생성되어 있습니다. `05`/`06`은 각각 4개 후보를 기술합니다. 승인 후 이름·prompt·run metadata를 일치시켜야 합니다.
- Track 1 profile JSON을 run 입력에 구조적으로 포함하거나 profile version/hash를 기록하는 기능은 아직 없습니다.
- Track 2 decision ledger에 대한 schema validation은 아직 없습니다. 현재 design schema의 `extensions`는 형식 자유 영역입니다.
- 현재 design schema는 flow 안의 field-level data contract와 Stitch manifest/screen-state traceability를 필수 검증하지 않습니다. Stitch tool도 agent의 다섯 workspace tool에 연결되어 있지 않습니다. 이를 구현하고 tool/version/handoff format을 고정하기 전에는 구현 handoff 산출물을 요구하는 기술 파일럿을 시작하지 않습니다.
- runner는 `07` 후보 JSON이 아니라 `hidden/changes/*.md`를 순서대로 읽습니다. gold test 실행 및 blind evaluator scoring도 아직 자동화되지 않았습니다.
- 실행 CLI는 draft의 `readyForRun:false`를 검사하지 않습니다. readiness gate 없이 조건 파일만 채워 실제 study를 시작하지 않습니다.
- 현재 runner는 선정된 Track 2 artifact를 hash 고정한 뒤 모든 Track 1 condition에 공통 seed로 주입하는 단계가 없습니다. seed manifest, 동일 workspace snapshot 복제, 별도 T1 run metadata 연결 기능을 추가하거나 동일한 절차를 외부에서 엄격히 기록해야 합니다.
