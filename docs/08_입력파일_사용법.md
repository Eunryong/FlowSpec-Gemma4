# 입력 파일 사용법

[여러 페이지 자료 뷰어 열기](연구자료_페이지/index.html)

## 지금 기준

- 연구할 서비스: **1:1 상담 예약 서비스**
- 난이도: **L2**
- 트랙 1: 개발자 설계 사고 프로필 + 장단점 보정
- 트랙 2: Revision-aware Design(변경을 고려한 설계)
- 아직 v1 요구사항이 승인되지 않아 모든 템플릿은 실험 실행용 최종본이 아닙니다.

## 현재 사용하는 파일

1. `00_연구_결정요약.md`: 합의된 내용과 아직 정하지 않은 점
2. `01_투트랙_연구방향_초안.md`: 두 연구의 질문과 범위 초안
3. `02_1대1상담예약_설계카드30개_초안.md`: 사람이 읽고 검토할 카드 30개
4. `03_상담예약_카드목록_입력용.json`: 카드 30개의 프로그램 입력용 목록
5. `04_공통_초기요구_템플릿.json`: 두 연구가 함께 사용할 초기 과제 설명의 틀
6. `05_트랙1_개발자프로필_입력템플릿.json`: 프로필 연구 조건과 프로필 정보의 형식
7. `06_트랙2_변경대응_입력템플릿.json`: 변경 대응 연구 조건과 결정 기록 형식
8. `07_트랙2_후속변경_연구자전용.json`: 초기 설계 뒤에만 공개할 변경 후보. 처음 AI 입력에 넣지 않습니다.

## 권장 순서

1. 설계 카드에서 실제 v1 요구를 승인하고 가정·미정·제외를 나눕니다.
2. 승인한 요구만 공통 초기요구 템플릿에 옮깁니다.
3. 공통 입력에 트랙 1 또는 트랙 2 템플릿 중 하나만 결합합니다.
4. 각 조건을 새 AI 대화에서 실행하고 입력·출력을 기록합니다.
5. 트랙 2는 첫 설계를 저장한 후 후속 변경 파일에서 요구 하나씩 공개합니다.

## JSON 파일의 영어 필드명

JSON 안의 `schemaVersion`, `reviewStatus`, `linkedIds` 같은 필드명은 프로그램이 읽기 쉽도록 영어로 유지했습니다. 뜻은 다음과 같습니다.

- `origin`: 카드 내용의 출처
- `reviewStatus`: 검토/승인 상태
- `decisionClass`: 안정된 결정, 잠정 결정, 가정, 미정 중 분류
- `linkedIds`: 연결된 카드 ID
- `validationCandidate`: 나중에 테스트로 확인할 후보
- `readyForRun`: 실제 실험을 시작해도 되는지 표시

현재 카드 30개는 아직 검토되지 않았고 `readyForRun=false`입니다. 숨은 변경 후보 파일은 별도로 격리했습니다.

## 실행 harness와 현재 연결 상태

사람 검토용 JSON은 현재 `run-experiment`가 직접 조립하거나 승인 상태를 검사하지 않습니다. 실행 전 아래 변환·검토가 필요합니다.

| 검토 자료 | 현재 harness 연결 | 실행 전 조치 |
|---|---|---|
| `03` 카드 catalog | 직접 읽지 않음 | 승인 카드만 공통 brief에 추출하고 출처·상태는 연구 artifact로 보존 |
| `04` 공통 초기요구 | `.json` brief로 전달은 가능하지만 readiness gate는 없음 | `readyForRun=false` 템플릿을 그대로 쓰지 말고 승인된 v1 요구만 brief로 정리 |
| `05` Track 1 템플릿 | 직접 읽지 않음 | 승인 condition 한 개를 `research/conditions/track1/<condition>.md`로 작성하고 profile 출처/version 관리 |
| `06` Track 2 템플릿 | 직접 읽지 않음 | 승인 condition 한 개를 `research/conditions/track2/<condition>.md`로 작성하고 ledger 검증 방식을 정함 |
| `07` 후속 변경 후보 | runner는 이 JSON을 읽지 않음 | 후보를 승인·정리한 뒤 `research/hidden/changes/change_XX.md`로 하나씩 분리. initial prompt에 포함하지 않음 |
| Gold tests | 내용 및 평가 실행기가 아직 없음 | `research/hidden/tests/`에 배치하고 blind evaluator 절차를 별도로 확정 |

runner는 `.md` 또는 `.json` brief, 트랙별 `.md` condition 하나, 공통 Designer/Coder prompt와 Design Specification schema를 읽습니다. 공통 run 시작 시에는 readiness 상태를 강제하지 않으므로 문서의 수동 gate를 먼저 통과해야 합니다. 실제 구현과 연구 문서의 간극 및 다음 단계는 [09 실행 플로우](09_연구_실행_플로우_및_의사결정_게이트.md), [10 서비스 설계 수준](10_상담예약_공통_설계레벨_초안.md), [11 트랙별 프로토콜](11_트랙별_실험설계_및_평가계획_초안.md)을 참고합니다.
