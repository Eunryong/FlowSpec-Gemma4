# [대체됨] 작업 스케줄러 L2 v1 설계 초안

**상태:** 사용자가 공통 연구 도메인을 예약 서비스로 변경해 이 초안은 superseded 처리했다. 이전 작업 스케줄러 제안은 기록용이며 현재 활성 설계로 사용하지 않는다. 로컬 시뮬레이션과 `run_at` 승인도 이 도메인에 자동 승계되지 않는다.

## 1. 목적과 범위

두 연구 트랙에서 사용할 공통 테스트 소프트웨어 후보: **단일 프로세스에서 작업을 접수·예약·실행·추적하는 작은 작업 스케줄러**.

L2 범위에 맞게 상태 전이와 저장, 여러 사용자 흐름, 실패·취소 경계를 포함한다. **확정된 실행 모델은 로컬 결정론적 시뮬레이션**이다. 실제 분산 서비스나 임의 사용자 코드를 실행하는 운영 scheduler는 만들지 않고, 테스트용 handler가 반복 가능한 성공·실패 결과를 돌려준다.

## 2. v1 사용자 흐름 제안

1. 작업 제출: 작업 종류, payload, 선택적 실행 시각을 전달한다. 실행 시각이 없으면 즉시 실행 대기 상태가 된다.
2. 작업 조회: ID로 상태·결과를 확인하고, 작업 목록을 본다.
3. 작업 예약: 미래 실행 시각이 된 작업을 대기열로 이동한다. 시간은 테스트 가능한 가상 clock을 사용한다.
4. 실행: 활성 worker 하나가 대기열에서 한 번에 하나의 작업을 실행한다. 같은 실행 시각이면 제출 순서 등 고정된 tie-break를 사용한다.
5. 종료: 결정론적 handler가 성공 또는 실패 결과를 돌려주며 상태와 결과를 저장한다.
6. 취소: 실행 전인 예약/대기 작업은 취소할 수 있다. 이미 실행을 시작한 작업의 취소는 v1에서 지원하지 않는 안이다.

## 3. 상태 흐름 제안

```text
미래 예약 ── 실행 시각 도달 ──> 대기 ──> 실행 중 ──> 성공
                                  │                └─> 실패
                                  └─> 취소
```

- 예약 시각이 지난 작업은 대기 상태로 이동한다.
- v1에서는 실패한 작업이 종료 상태로 남고 자동 재시도하지 않는다.
- 작업 기록·상태·결과는 저장한다. 실행 중 프로세스가 비정상 종료된 작업을 자동 복구하는 보장은 v1에서 약속하지 않는다.
- 작업의 반복 일정(cron), 우선순위, 다중 worker, 분산 실행은 초기 범위에 넣지 않는다.

## 4. 예상되는 L2 경계와 테스트 가능한 경우

- 정상 흐름: 제출 → 예약/대기 → 실행 → 성공
- 실패 흐름: handler 실패 → 실패 상태와 오류 결과 기록
- 취소 경계: 실행 전 취소 가능, 실행 시작 후는 불가
- 순서 경계: 동일 시각에 준비된 여러 작업의 결정론적 순서
- 입력 경계: 알 수 없는 작업 종류 또는 잘못된 payload
- 저장 경계: 작업 상태와 결과의 저장 및 일반 재실행 후 조회

위 항목은 v1 요구로 제안한 것이며, 어떤 경계 사례를 명시 요구로 두고 어떤 것을 미지정/후속 변경으로 남길지는 사용자 확인이 필요하다.

## 5. 연구 트랙별 사용 방식

### Track 1 — Revision-aware Design

모든 조건은 같은 v1 요구에서 출발한다. 추후 추가 요구는 설계 생성 시 숨긴다. 변경 후보는 예를 들어 다음처럼 규모가 다른 요구일 수 있다.

- 같은 실행 시각의 우선순위 정책 추가
- 실패 작업에 제한된 재시도와 backoff 추가
- 작업자가 여러 개일 때 중복 실행 방지 또는 재시작 후 복구 추가

이는 후보 목록이며, 변경 난이도·순서·정답 테스트는 아직 확정하지 않았다.

### Track 2 — 개발자 설계 사고 프로필 + 보정

같은 scheduler 문제를 쓰되, Agent에게 일반 검토 절차 또는 근거가 있는 개발자별 검토 프로필을 제공하는 방향이다. 중복 제출, 실행 시작과 취소의 경계, 같은 시각 작업 순서, 실패 후 상태 같은 경우가 프로필의 edge-case 탐색 이득을 드러낼 수 있다.

프로필이 발견한 모든 가능성을 구현 요구로 바꾸지 않고, 명시 요구·필수 안전/정합성·합리적 가정·후속 제안으로 구분하는 보정이 필요하다. 세부 실험군은 연구 프로토콜 단계에서 정한다.

## 6. v1에서 제외할 제안 범위

- 다중 사용자 인증·권한
- 실제 결제, 이메일, 외부 API, 임의 사용자 스크립트 실행
- 여러 서버/분산 큐, 네트워크 파티션, 운영 부하·성능 보증
- 다중 worker와 동시성 제어
- cron·반복 작업
- UI polish와 배포 파이프라인

## 7. 아직 선택이 필요한 설계 질문

1. 인터페이스를 CLI, 로컬 API, 또는 테스트용 라이브러리 중 무엇으로 둘지.
2. 저장소를 v1 요구로 포함할지, 포함한다면 단일 로컬 저장소 정도로 한정할지.
3. 가상 시각의 단위·정밀도와 동시 실행 시 tie-break 규칙.
4. 취소를 예약/대기 상태에서만 허용하는 제한이 적절한지.
5. v1에서 실패 결과 기록을 필수로 하고, retry는 후속 변경으로 둘지.
6. Track 1의 숨겨진 변경 요청을 몇 개 둘지, 각각 로컬·정책·교차모듈 변경 중 어느 수준인지.

> **다음 단계는 이 초안의 범위 확인이다.** 승인 후에만 v1 요구와 후속 변경 요구를 분리한 정식 요구사항 초안을 만들고, 아직 코드는 작성하지 않는다.
