연구 아이디어 대화 정리

현재까지 나온 연구 방향, 서로 다른 질문의 경계, 확인된 선행연구의 범위, 아직 정하지 않은 항목을 한곳에 정리했습니다. 사용자가 의도한 내용과 제 해석을 구분했으니, 맞지 않는 부분을 표시해 수정할 수 있습니다.

현재 버전: v0.2 · 개인화 설계 과정 후보 추가 · 연구주제 확정본이나 체계적 문헌고찰은 아님
내가 이해한 의도연구 방향 지도Revision-aware개발 사고방식 개인화근거 확인미결정 항목출처

1. 내가 이해한 사용자의 의도

가장 중요한 구분: Revision-aware design과 이번에 추가한 developer-reasoning personalization은 각각 별도 연구 후보입니다. 둘 다 앞서 논의한 계획 품질·근거 조사 방향과 자동으로 합치지 않습니다.
  • 사용자 발언 비개발자와 개발자의 집단 차이를 메인 독립변수로 삼기보다, 비개발자 요청을 사용 시나리오로 두는 방향을 고려함.
  • 사용자 발언 앞서 제안한 1차 실험은 구현까지 가지 않고 계획/설계 산출물의 품질에 먼저 한정하는 방향.
  • 사용자 정정 연구를 무조건 한데 묶거나 무조건 나누자는 고정 규칙은 아님. 경계가 분명하면 독립 후보로 평가하고, 겹치는 부분이 클 때만 통합 여부를 따짐.
  • 별도 후보 1 설계 시점에 확정된 요구와 임시 가정·변경 가능 지점을 구분하게 해, 나중의 예상하지 못한 변경에도 과도한 추상화 없이 대응하는 설계를 만들 수 있는지.
  • 별도 후보 2 개발자에게서 반복 관찰된 설계·검토 사고방식을 에이전트가 활용하고, 그 부작용까지 보정하면 최종 설계와 구현 품질이 좋아지는지.
범위 주의: “계획 품질만 측정”은 이전의 1차 파일럿 제안에 붙은 범위입니다. Revision-aware와 개인화 후보에서 실제 변경 적응성 또는 downstream 구현 품질을 주장하려면 후속 변경·구현 평가가 필요할 수 있습니다. 어느 한 범위를 다른 후보에 자동 적용하지 않았습니다.

2. 지금까지 나온 연구 방향 지도

각 행은 서로 다른 조작변수와 결과를 가진 후보입니다. 같은 큰 관심사인 “에이전트가 더 나은 설계를 하도록 돕는 방법”에 닿지만, 같은 질문은 아닙니다.

후보무엇을 바꾸거나 비교하나주요 결과구현이 필요한가
A. 사용자 시나리오와 계획 품질기능 요구만 / 사용자 시나리오 추가 / 시나리오와 제약 추가요구 반영, 근거 없는 가정, 범위 확장, 미결정 질문, 반복 안정성초기 파일럿은 불필요
B. 사전 설계 워크플로바로 설계 / 자기 분석 / 외부 자료 조사 / 조사 후 독립 검토근거성, 요구 충족, 실현가능성, 불확실성 처리, 비용계획 품질만 보는 1단계에선 불필요
C. 초기 아키텍처 투자량Minimal 대 Extensible 설계 후 변경을 단계별 공개초기 비용과 변화 누적 비용의 역전 지점, 회귀, 수정량변경 적응성을 보려면 구현/수정 평가가 유리
D. 사전 검증의 경제성즉시 구현 / 자기검토 / 구조화 검증 / 강한 검증검증 비용 대 구현 이후 재작업·결함·총비용실제 재작업 절감 주장에는 필요
E. Revision-aware design
별도 후보		일반 설계 / 막연한 확장성 지시 / 결정의 안정성·가정·변경점 명시숨겨진 변경 요구에서 적응성, 과잉설계, 비용변경에 대한 성능을 보려면 후속 변경 평가 필요
F. 개발자 사고방식 개인화
새 별도 후보		일반 에이전트 / 일반 검토 절차 / 개인별 관찰 프로필 / 프로필 활용+부작용 보정누락된 예외·실패 경로, acceptance·회귀, 과잉설계, 비용최종 소프트웨어 품질 주장은 downstream 구현·테스트 필요
이해 확인: A는 요청 정보, B는 사전 설계 과정, C는 초기 아키텍처 투자량, D는 검증량, E는 변경 가능성을 표현하는 방법, F는 개발자별 사고·검토 습관을 에이전트의 설계 과정에 활용하는 방법을 묻습니다.

3. 별도 후보: Revision-aware design

설계 Agent가 확정된 사실과 임시 결정·가정을 구분하고, 변경 가능 지점과 재검토 조건을 기록하게 하면, 아직 공개하지 않은 요구사항 변경에 더 적은 비용과 과잉설계로 대응할 수 있는가?

사용자가 제안한 설계 기록 항목

확정·불확실성

USER REQUIREMENT, STABLE DECISION, PROVISIONAL DECISION, ASSUMPTION

변경 준비

CHANGE POINT, 영향받는 모듈, REVISIT CONDITION을 표시해 변경 때 무엇을 다시 볼지 기록

조건 예시 (아직 확정 아님)

조건가능한 지시분리해 보는 효과
A. 일반 설계요구사항에 맞는 설계를 작성기준선
B. 일반적 확장성미래 확장을 고려해 설계막연한 확장성 지시가 과잉설계를 유발하는지
C. 절제된 변경대응변경 가능성을 고려하되 불필요한 추상화는 피함일반 지시보다 균형이 좋아지는지
D. 명시적 decision ledger안정/임시/가정/변경점/재검토 조건을 구조화해 기록구조화된 불확실성 기록의 추가 효과

핵심 평가 원칙

  • 설계 생성 시 미래 변경 요구를 알려주지 않고, 초기 설계 후 단계별로 공개한다. 그래야 미래 정답을 미리 넣은 효과와 변경에 강한 설계를 구분할 수 있다.
  • 초기 구현의 정확도와 변경 후 정확도 모두 본다. 변경량이 적다는 사실만으로 좋은 설계라고 판정하지 않는다.
  • 변경 때의 회귀, 변경에 필요했던 수정 파일/LOC, 불필요한 abstraction·dependency, token/tool/time 비용을 함께 측정한다. LOC 단독 지표는 품질의 대리값으로 쓰지 않는다.
  • 숨겨진 요구의 성격을 “초기 정보에서 추론 가능했던 조건”과 “새로 추가된 기능 요구”로 구분한다.
정의가 더 필요한 부분: “Stable”과 “Provisional”을 누가 어떤 근거로 판정하는지, “과잉설계”를 어떤 기준으로 점수화할지, 알려지지 않은 사용자 선호를 모델이 질문해야 하는지 가정해야 하는지 아직 미정입니다.

4. 새 별도 후보: Personalized design process

이 후보의 중심: 사용자 취향에 맞는 UI나 personality profile이 아니라, 개발자가 설계하고 검토할 때 반복해서 보이는 사고·검토 행동을 에이전트가 활용하는 것. Revision-aware 후보와도 독립적으로 평가합니다.

개발자의 반복적으로 관찰된 설계·검토 행동을 에이전트의 사전 설계 과정에 적용하면, 일반적인 방법보다 누락된 설계 결함과 downstream 구현 결함을 줄일 수 있는가? 그리고 좋은 습관은 활용하면서 그 체계적인 부작용은 보정할 수 있는가?

관찰 가능한 행동으로 프로필을 만든다

관찰 패턴활용할 수 있는 강점가능한 부작용
실패·경계·분기 조건을 반복해서 질문예외 경로와 누락된 요구를 조기에 발견낮은 가능성의 가정까지 전부 기능·구조에 반영해 범위가 불어남
재시도·중복 호출·동시성·중간 종료를 확인회복성·상태 일관성 문제를 찾음현재 요구와 무관한 복잡한 방어 설계가 늘어남
단순성·필요성·요청 범위를 자주 재검토불필요한 abstraction과 기능 확장을 억제필요한 안전장치나 장기 제약을 놓칠 수 있음

위 행동은 예시이지 사용자의 확정된 성격 진단이 아닙니다. 각 프로필 항목은 관찰 근거, 반복 빈도, 적용되는 과제 맥락, 신뢰도를 포함하고 사용자가 확인·수정할 수 있게 하는 안이 적절합니다.

실험 비교안 (아직 제안 단계)

조건설계 절차에 주는 정보비교 목적
A. Generic baseline개발자별 정보 없이 일반 설계 수행기준 성능
B. Generic review protocol모든 참가자에게 동일한 edge/failure-case 검토 절차 제공개인화가 단순한 일반 체크리스트보다 나은지
C. Naive personalization개인 프로필에 나타난 검토 습관을 그대로 강화습관 모방의 이득과 부작용
D. Compensated personalization유효한 습관은 활용하고, 과잉설계 등 관찰된 부작용은 억제개인화+보정이 가장 균형 있는지
권장되는 구분: 프로필을 “어떻게 얻는가”와 그 프로필을 “설계에 어떻게 쓰는가”는 서로 다른 질문입니다. 첫 실험에서는 프로필 생성법을 고정·검증한 뒤, 사용 방식(A–D)의 효과를 비교해야 두 효과가 섞이지 않습니다.

평가 후보와 주요 위험

  • 프로필 정확도: 과거 자료에서 추출한 패턴이 새로운 과제에서도 재현되는가? 프로필은 한 번의 대화가 아니라 여러 설계·검토 세션과 근거에 기반해야 합니다.
  • 설계·구현 품질: 요구/경계조건 누락, acceptance·hidden-test 통과, 실패 경로, 회귀, 재작업 횟수와 시간.
  • 과잉설계와 비용: 불필요한 abstraction·기능, 설계 복잡성, token/tool 사용량. 질문·테스트를 많이 만든 것만으로 개선이라고 하지 않습니다.
  • 일반 절차 비교가 중요합니다. 개인화가 단순한 공통 edge-case 체크리스트보다 나아지지 않으면, 효과는 개인화가 아니라 일반적인 검토 절차에서 온 것일 수 있습니다.
  • 여러 개발자를 포함하지 않으면 보편적인 효과가 아니라 단일 사용자 사례/타당성 파일럿으로 해석해야 합니다. 프로필 추론에는 사용자 동의·수정권과 근거 표시도 필요합니다.
평가: 개인화 연구 자체는 이미 있습니다. 이 후보의 유망한 차별점은 “개발자 취향을 저장한다”가 아니라, 반복 관찰된 설계 검토 전략을 프로세스에 적용하고, 이득과 역효과를 함께 측정하며, 역효과를 보정하는 것입니다. 다만 신규성은 문헌을 더 넓게 검색하기 전까지 주장하지 않습니다.

5. 이전 1차 후보: 계획 품질만 보는 파일럿

이 실험은 Revision-aware 및 개인화 후보와 분리해 보존했습니다. 같은 기능 요청에 정보를 단계적으로 더 주고, 코드 없이 계획 산출물만 평가하는 안입니다.

A · Basic Request
기능 요구만 제공
→
B · + User Scenario
사용자·업무 흐름 추가
→
C · + Constraints
환경·운영 제약 추가

주 비교: A 대 B는 시나리오 정보의 효과. B 대 C는 제약조건 추가 효과. 따라서 C를 “시나리오 효과”만으로 해석하지 않습니다.

계획 점수 후보: workflow 반영, 요구 누락, 근거 없는 확정, 요청 밖 기능의 필수화, 기술/환경 적합성, 미결정 사항 질문, 반복 실행 간 주요 결정 일치도.

5개 과제 × 3조건 × 3회 = 45개 산출물은 파일럿으로는 쓸 수 있지만, 일반적 효과를 주장할 정도의 표본이라고 미리 가정하면 안 됩니다.

6. 인용된 선행연구: 확인된 내용과 한계

아래는 초록·원문에서 확인한 범위입니다. 이것은 체계적 문헌고찰이나 신규성 증명이 아닙니다. “비슷한 문제를 다룬다”와 “같은 실험을 했다”를 구분했습니다.

연구확인한 범위현재 아이디어와의 관계 / 한계
SWE-RPG (2026)저장소 과제에서 요구 명확화·계획·코드 생성을 함께 진단. 요구 복원 실패가 평가 실행의 주요 병목으로 분류됨.요구 누락의 중요성을 뒷받침. 특정 사전설계 워크플로가 이를 해결한다는 증거는 아님.
SpecBench (2026)초기 설계 제안의 누락·모호함·모순·잘못된 가정을 탐지하는 능력을 평가. 최고 보고 정확도 44.4%.설계 결함 탐지가 어렵다는 증거. 초기 버전은 결함 탐지 중심이며, 개선된 spec의 구현 효과를 직접 입증하지 않음.
MAAD (2026)Analyst/Modeler/Designer/Evaluator, RAG, 계층적 memory와 iterative refinement로 요구사항에서 architecture 산출.근거 조사·설계·평가 워크플로와 가까움. revision-aware decision ledger와 숨겨진 미래 변경 평가를 동일하게 시험한 것은 아님.

7. 아직 결정되지 않은 질문

  1. 지금 우선 평가할 후보: 계획 품질, evidence-grounded workflow, architecture investment, validation dose, revision-aware design 중 무엇인가? 최신 아이디어는 앞선 것과 별도 후보로 표시됨.
  2. 대상 환경: 빈 프로젝트에 새 프로그램을 설계하는가, 기존 저장소의 변경을 설계하는가? Repository 탐색의 의미가 달라짐.
  3. 1차 단계 경계: 계획 문서만 평가할 것인가, revision-aware 후보의 후속 변경 과제까지 포함할 것인가?
  4. 정답표/평가자: 요구 충족, 근거 없는 가정, overengineering, 변경 영향은 어떤 전문가 rubric 또는 테스트로 채점할 것인가?
  5. 개발자 프로필: 어떤 반복 관찰을 근거로 만들고, 추론 프로필과 사용자 확인 프로필을 구분할 것인가? 과제별로 달라지는 성향을 어떻게 기록할 것인가?
  6. 개인화 대 일반 절차: 공통 edge-case checklist보다 개인화가 추가 이득을 주는지, 그리고 보정 조건이 순수 프로필 모방보다 과잉설계를 줄이는지 비교할 것인가?
  7. 모델과 실행 조건: 정확한 Gemma 4 모델 ID/version, temperature, 반복 횟수, 토큰·도구 예산을 어떻게 고정할 것인가?
  8. 통합/분리: 질문 경계와 공통 실험이 정해진 뒤 판단. 현재 문서에서는 어느 쪽도 영구 규칙으로 못 박지 않음.
이 문서의 목표: 다음 단계로 넘어가기 전에 “내가 전달한 연구 의도”와 “제가 덧붙인 해석·권고”를 서로 구분해 사용자가 바로잡을 수 있게 하는 것.
