# 1:1 상담 예약 서비스 v1 Design Cards — 검토 초안 v0.2

**상태:** 공통 도메인 “1:1 상담 예약 서비스”와 L2 난이도는 확인됨. 상담 분야와 v1 규칙은 미정이며, 아래 카드 내용은 승인 전 검토용 제안이다. 이전 작업 스케줄러의 실행 방식·시간 예약 결정은 승계하지 않는다.

## 카드 원칙

각 카드는 한 가지로 틀릴 수 있는 설계 판단·흐름·규칙을 담는다. 색상·margin 같은 구현 디테일은 카드로 만들지 않는다.

**공통 필드:** `ID`, `Type`, `Statement`, `Origin`, `Review status`, `Links`, `Validation/Open question`.

- `U-example`: 사용자가 예시로 든 내용. 서비스의 확정 요구로 간주하지 않음.
- `Draft`: 이번 초안에서 제안한 내용.
- `Open`: 답이 정해지지 않은 선택·요구.
- `Review status`: 현재 카드는 모두 `UNREVIEWED`. 승인 후 `ACCEPTED`, `PROVISIONAL`, `REJECTED` 등으로 갱신.
- Revision-aware 실험에서는 `stable / provisional / assumption`을 카드 내용과 구분되는 별도 decision metadata로 시험한다.

총 30개 후보 카드다. 수량은 초안 검토용 목표이며, 중복·불필요 카드가 보이면 줄인다.

## 1. Product Goal (1)

### [PG-01] 1:1 상담 예약의 목표
- **Statement:** 고객이 상담자의 가능 시간을 확인하고 1:1 상담을 예약할 수 있다.
- **Origin:** U-example · **Links:** ACT-01, FLOW-01, FLOW-02 · **Review:** UNREVIEWED
- **Validation:** 고객이 가능한 시간 탐색에서 예약 결과 확인까지 완료하는 테스트 흐름이 있어야 한다.

## 2. Actor / Role (2)

### [ACT-01] 고객
- **Statement:** 고객은 서비스/시간을 확인하고 예약을 생성한다. 예약 조회·취소 권한은 별도 확인한다.
- **Origin:** U-example + open · **Links:** FLOW-01–04 · **Review:** UNREVIEWED
- **Open question:** 로그인 또는 예약번호 기반 접근 중 무엇인가?

### [ACT-02] 상담자
- **Statement:** 상담자는 자신의 예약 가능 시간을 제공·관리하고 배정된 상담 일정을 확인한다.
- **Origin:** Draft · **Links:** FLOW-05, DOM-02 · **Review:** UNREVIEWED
- **Open question:** 상담자가 직접 관리하는가, 별도 운영자 역할이 필요한가?

## 3. User Flow (5)

### [FLOW-01] 상담 유형·상담자·날짜별 가능 시간 찾기
- **Statement:** 고객이 상담 분야/상담자와 날짜를 선택해 가능한 상담 시간을 확인한다.
- **Origin:** U-example · **Links:** PG-01, DOM-01, DOM-02, UI-01, UI-02 · **Review:** UNREVIEWED
- **Validation:** 해당 날짜의 열림/닫힘 시간대와 예약 상태가 결과에 반영된다.

### [FLOW-02] 예약 생성
- **Statement:** 고객이 시간대를 선택하고 필수 정보를 입력한 뒤 예약을 제출한다.
- **Origin:** U-example · **Links:** DOM-02, DOM-03, RULE-01, RULE-02, UI-03 · **Review:** UNREVIEWED
- **Validation:** 성공 시 한 건의 예약이 만들어지고 선택한 시간대와 연결된다.

### [FLOW-03] 예약 결과 확인
- **Statement:** 예약 제출 뒤 성공 또는 실패 결과를 고객에게 보여준다.
- **Origin:** Draft · **Links:** DOM-03, UI-04 · **Review:** UNREVIEWED
- **Open question:** 즉시 확정인가, 관리자 승인 대기인가?

### [FLOW-04] 예약 조회·취소
- **Statement:** 고객이 기존 예약을 찾아 상세 정보를 확인하고, 허용 조건을 만족할 때 취소한다.
- **Origin:** Draft · **Links:** DOM-03, EDGE-04, DEC-01 · **Review:** UNREVIEWED
- **Open question:** 조회와 취소를 v1에 모두 넣을 것인가? 취소 가능 시점은 언제인가?

### [FLOW-05] 상담자의 가능 시간 관리
- **Statement:** 상담자가 상담 가능 시간을 등록·닫거나 예약 일정을 확인한다.
- **Origin:** Draft · **Links:** ACT-02, DOM-02, RULE-03 · **Review:** UNREVIEWED
- **Open question:** 상담자가 이미 예약된 시간대를 닫을 때 기존 예약을 어떻게 처리하는가?

## 4. Domain / State (4)

### [DOM-01] 상담 유형
- **Statement:** ConsultationType은 상담 유형의 식별자와 표시 정보를 보유한다.
- **Origin:** Draft · **Links:** FLOW-01, DOM-02 · **Review:** UNREVIEWED
- **Open question:** 서비스별 소요시간·가격·담당 자원이 v1에 필요한가?

### [DOM-02] 상담자 가능 시간대
- **Statement:** 상담 시간대는 상담자, 시작·종료 시각, 예약 가능 여부를 연결한다.
- **Origin:** Draft · **Links:** FLOW-01, FLOW-02, RULE-01–03 · **Review:** UNREVIEWED
- **Open question:** 시간대는 미리 생성되는가, 영업시간 규칙에서 계산되는가?

### [DOM-03] 예약
- **Statement:** 예약은 고객 1명, 상담자 1명, 선택 시간대, 식별자와 현재 상태를 연결한다.
- **Origin:** Draft · **Links:** FLOW-02–04, STATE-01 · **Review:** UNREVIEWED
- **Validation:** 예약 한 건을 시간대·고객·상태와 함께 다시 조회할 수 있다.

### [STATE-01] 예약 상태와 전이
- **Statement:** 사용자 예시 상태는 `CONFIRMED`와 `CANCELLED`. 별도 운영자 승인 방식이면 `PENDING`이 필요한지 결정해야 한다.
- **Origin:** U-example + open · **Links:** DOM-03, FLOW-03–04 · **Review:** UNREVIEWED
- **Open question:** 허용 상태와 각 상태의 전이 규칙은 무엇인가?

## 5. Business Rule (4)

### [RULE-01] 같은 시간대의 중복 활성 예약 금지
- **Statement:** 같은 상담자의 같은 시간대에는 활성 예약을 하나만 허용한다.
- **Origin:** U-example · **Links:** DOM-02, DOM-03, FLOW-02, EDGE-01 · **Review:** UNREVIEWED
- **Validation:** 동시 예약 시도 두 건 중 최대 하나만 성공한다.

### [RULE-02] 제출 시 가능 여부 재검증
- **Statement:** 예약 제출 시점에 해당 상담자의 시간 가능 여부를 다시 확인하고 확보해야 한다.
- **Origin:** Draft · **Links:** FLOW-02, RULE-01, EDGE-01 · **Review:** UNREVIEWED
- **Validation:** 조회 후 다른 고객이 먼저 예약한 시간은 후속 제출에서 거절된다.

### [RULE-03] 닫힌 시간대 예약 금지
- **Statement:** 상담자가 닫았거나 운영 불가로 표시된 시간에는 새 상담 예약을 받을 수 없다.
- **Origin:** Draft · **Links:** ACT-02, FLOW-05, DOM-02, UI-02 · **Review:** UNREVIEWED
- **Validation:** 닫힌 시간대는 선택 불가하고 직접 제출도 거부된다.

### [RULE-04] 제출 후 즉시 확정 여부
- **Statement:** 유효한 요청과 슬롯 확보에 성공하면 즉시 `CONFIRMED`로 전이하는 안이다. 별도 운영자 승인 여부는 미정이다.
- **Origin:** Draft/Open · **Links:** STATE-01, FLOW-03, UI-04 · **Review:** UNREVIEWED
- **Open question:** 즉시 확정과 별도 운영자 승인 중 어느 정책을 v1로 선택할 것인가?

## 6. UI / Interaction (4)

### [UI-01] 상담 조건 선택
- **Statement:** 고객이 상담 분야/상담자와 날짜를 선택해 가능 시간 조회를 시작한다.
- **Origin:** U-example · **Links:** FLOW-01, DOM-01 · **Review:** UNREVIEWED
- **Validation:** 서비스/날짜가 바뀌면 시간대 목록도 해당 조건으로 갱신된다.

### [UI-02] 가능 시간 표시·선택
- **Statement:** 예약 가능한 시간만 선택할 수 있고, 예약 불가능한 시간은 상태가 구분된다.
- **Origin:** U-example · **Links:** FLOW-01–02, RULE-03 · **Review:** UNREVIEWED
- **Validation:** 비활성 시간대를 직접 제출해도 서버 측 규칙이 거부한다.

### [UI-03] 예약 정보 입력
- **Statement:** 고객은 필수 예약자 정보를 입력하고 제출 전 오류를 확인할 수 있다.
- **Origin:** Draft · **Links:** FLOW-02, EDGE-03 · **Review:** UNREVIEWED
- **Open question:** v1에서 필요한 최소 고객 정보는 무엇인가?

### [UI-04] 예약 결과와 오류 안내
- **Statement:** 성공·시간대 충돌·입력 오류를 구별해 결과를 안내한다.
- **Origin:** Draft · **Links:** FLOW-03, RULE-02, EDGE-01–03 · **Review:** UNREVIEWED
- **Validation:** 실패가 성공처럼 보이지 않고, 다시 시도할 수 있는 경우가 안내된다.

## 7. Failure / Edge Case (4)

### [EDGE-01] 조회 후 제출 전에 시간대가 선점됨
- **Statement:** 고객이 선택한 뒤 다른 요청이 먼저 같은 시간대를 예약할 수 있다.
- **Origin:** U-example · **Links:** RULE-01–02, UI-04 · **Review:** UNREVIEWED
- **Validation:** 두 제출 중 하나만 성공하며 실패한 고객에게 최신 상태가 안내된다.

### [EDGE-02] 중복 제출 또는 응답 유실 후 재시도
- **Statement:** 더블 클릭·네트워크 재시도 때문에 같은 예약이 두 번 생성될 수 있다.
- **Origin:** Draft · **Links:** FLOW-02, DOM-03, RULE-01 · **Review:** UNREVIEWED
- **Open question:** 중복 요청을 막는 idempotency가 v1 요구인가, 후속 변경 후보인가?

### [EDGE-03] 예약자 정보 누락·형식 오류
- **Statement:** 필수 연락 정보가 누락되거나 허용 형식에 맞지 않을 수 있다.
- **Origin:** Draft · **Links:** FLOW-02, UI-03–04 · **Review:** UNREVIEWED
- **Validation:** 잘못된 정보는 예약으로 저장되지 않고 수정 가능한 오류가 반환된다.

### [EDGE-04] 잘못된 번호·이미 취소된 예약을 조회/취소
- **Statement:** 예약번호가 없거나, 이미 취소된 예약에 다시 취소 요청이 올 수 있다.
- **Origin:** Draft · **Links:** FLOW-04, DOM-03, STATE-01 · **Review:** UNREVIEWED
- **Open question:** 존재하지 않음과 이미 취소됨을 UI/API에서 어떻게 구분할 것인가?

## 8. Assumption / Decision (6)

### [DEC-01] 로그인 없이 예약번호로 조회
- **Statement:** 고객 계정 없이 예약번호를 발급해 예약을 찾는 안이다.
- **Origin:** U-example · **Links:** FLOW-04, DOM-03 · **Review:** UNREVIEWED · **Decision class:** 아직 미지정
- **Open question:** 개인정보 접근을 보호하기에 충분한가?

### [OPEN-01] 상담자 수와 배정 방식
- **Statement:** 상담자가 한 명인지 여러 명인지, 고객이 상담자를 선택하는지 운영자가 배정하는지 미정이다.
- **Origin:** Open · **Links:** ACT-02, DOM-01–02, RULE-01, FLOW-01, FLOW-05 · **Review:** UNREVIEWED

### [OPEN-02] 취소·변경 정책
- **Statement:** 고객 취소와 재예약 허용 시점 및 제약을 정해야 한다.
- **Origin:** Open · **Links:** FLOW-04, STATE-01 · **Review:** UNREVIEWED
- **Open question:** 취소 가능 시점과 재예약 지원 여부는 무엇인가?

### [OPEN-03] 시간대 생성 정책
- **Statement:** 영업 가능 구간에서 예약 시간대를 고정 간격으로 생성하는지, 상담자 또는 운영자가 개별 시간대를 입력하는지 미정이다.
- **Origin:** Open · **Links:** DOM-01–02, FLOW-01, FLOW-05, RULE-03 · **Review:** UNREVIEWED
- **Open question:** 서비스별 소요시간과 영업시간을 어떻게 적용하는가?

### [OPEN-04] 시간대의 기준 시간
- **Statement:** 저장·표시 시각을 서비스 장소의 현지 시간 또는 UTC 기준으로 다룰지 정해야 한다.
- **Origin:** Open · **Links:** DOM-02, FLOW-01, RULE-03 · **Review:** UNREVIEWED
- **Open question:** 서비스 위치와 일광절약시간을 지원 범위에 넣을 것인가?

### [OPEN-05] 상담 분야와 예약 시 수집 정보
- **Statement:** 상담 분야와 예약 단계에서 수집할 정보(연락처만인지, 상담 주제/메모도 포함하는지)가 미정이다.
- **Origin:** Open · **Links:** ACT-01, FLOW-02, DOM-03, UI-03 · **Review:** UNREVIEWED
- **Open question:** 상담 내용이나 민감한 세션 기록을 예약 시스템에 저장할 필요가 있는가?

## 두 연구 트랙에서 카드가 쓰이는 방식

- **개발자 사고 프로필:** 프로필이 추가한 규칙/edge case 카드가 타당한지, 구현에 반영할지 보류할지, 복잡성을 얼마나 늘리는지 평가한다. 카드 개수 자체를 품질 점수로 쓰지 않는다.
- **Revision-aware design:** 카드의 결정 상태, 근거, `affects` 관계, 재검토 조건을 기록하고, 이후 변경으로 실제 영향을 받은 카드와 놓친 카드를 추적한다.
- 두 트랙이 같은 예약 서비스 카드를 참고하더라도 조건과 결론은 독립적으로 유지한다.

## 아직 확정하지 않은 핵심 질문

1. 상담의 구체 분야와 예약 단계에서 저장할 정보 범위가 무엇인지.
2. 상담자가 직접 가능 시간을 관리하는지, 별도 운영자가 필요한지.
3. 즉시 확정, 로그인 방식, 취소 정책, 자원 수용량을 어떻게 정할지.
4. 실제 결제 없이 결정론적 test harness만 두는 것이 맞는지.
5. 이 30개 중 어떤 카드를 baseline 요구로 확정하고 어떤 카드를 가정·미지정으로 둘지.

> 다음 단계에서는 우선 `Origin`과 `Review status`를 바탕으로 카드마다 **확정 요구 / 가정 / 미결정 / 제외**를 판정한다. 그 확인 전에는 이 카드를 구현 명세로 사용하지 않는다.
